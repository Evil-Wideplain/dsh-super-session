# Personal Agent, Worker and Coordinator

Three DSH agent presets shipped by one bundle: a shell-first personal assistant, a worker session for briefed delegation, and a coordinator that holds one goal and dispatches workers. All keep a deliberately small tool surface.

## What it adds

- A **personal** preset (`personal`, "Personal Agent"): a personal-agent persona and an operating handbook, in English and Chinese. The handbook is a near-verbatim port of Meta Muse's system prompt (values, one-user loyalty, discretion, external parties, design of work, personalization and memory, context awareness, active work, writing style, tools, delegation, scheduled work, runtime files, security, safety), with facts swapped for DSH's tool surface, plus DSH-specific sections on skills, worker-session delivery, scheduled-task verification, file delivery, first run and continuity.
- A **worker** preset (`worker`, "Worker"): the standard preset's coding-agent persona line plus a worker handbook, in English and Chinese. The handbook is a DSH-style operating prompt adapted to a persistent single-task worker: the brief is the objective, the session keeps going across rounds instead of asking permission between steps, work is explored before it is changed and verified before it is reported, and the result goes back to the lead with `send_session_message`. It deliberately does not repeat the personal handbook.
- A **manager** preset (`manager`, "Coordinator"): a coordinator persona and a short handbook, in English and Chinese. It takes one goal from a lead agent, keeps it as a goal across rounds, splits it into briefs for worker sessions, accepts their evidence, and reports back. It creates worker sessions only — never a `personal` or another `manager` session — and it neither addresses the user nor does the work itself. That limit is runtime-enforced: the bundle's `guard.js` hides the global `create_session_agent` inside the manager's tool scope and exposes `dispatch_worker`, whose Agent preset is fixed to `worker`.
- A sidebar panel row **Super Session** (above the workspace list): it is your one standing session, and selecting it opens that conversation directly with no intermediate page. The panel identifies it by a fixed Session id, `session-super-session` — a plain string, because DSH accepts any Session id — and keeps it attached to the built-in workspace `<Documents>/deepseek-harness/super-workspace`, titled `Super Workspace` and sitting beside DSH's own `default-workspace`. Membership is required: the Conversation replaces the composer of a blank Session that belongs to no workspace with a “choose a workspace” picker, so the panel creates the Session with `workspaceId` (never together with `cwd`, which the Host refuses) and the Host attaches it in the same call; a Session an earlier version created from `cwd` alone is attached by the Host at startup. The Host also creates the directory and registers the workspace, and the group is hidden from the sidebar's Workspace tree: DSH has no Workspace visibility flag, and filtering the shared Workspace store would change real state, so the client hides only that one group at the display layer with a style element keyed on the tree row's `data-row-key`, removed when the plugin is disposed. The Session is reached only through this panel row, by its fixed id. The panel recognizes the workspace by the `deepseek-harness/super-workspace` path tail or by its exact title to read its identity and path. The first click creates the Session on the `personal` preset titled `Super Session`; later clicks reopen that same id, unarchiving it first if the user archived it, and put it back on `personal` while it is still blank, because a plain “new session” click inside that workspace can reuse the blank Session and switch it to the current default preset. When the workspace is not there, the panel reports that a DSH restart will create it and offers a retry; when the fixed Session exists but is not attached, it reports that a restart will attach it. A Session an earlier version created under a different id inside that workspace is not adopted: it stays an ordinary member with its history. It adds no tools; it calls the existing session and workspace services.
- Mounted tools for the personal preset: a persistent shell (`bash` on non-Windows, `pwsh` on Windows), `schedule_*`, `create_goal` / `get_goal` / `update_goal`, `todo_write`, plan mode + `exit_plan_mode`, `ask_user_question`, `present`, and `skill`. It mounts none of the tools that execute: no `read_image`, no `job_*`, no `web_search` / `web_fetch`, no Office tools. The personal preset dispatches that work to a worker session instead of doing it. Its skill discovery keeps the default roots, so the catalog carries the user's own skills, whatever the session's project ships in `.dsh/skills` or `.agents/skills` (resolved from the session's working directory on every lookup), `dsh-doc` from the agent-preset package, and the four Office skills from the profile-level provider.
- Mounted tools for the worker preset: the same persistent shell and `read_image`, `job_output` / `job_list` / `job_kill`, `todo_write`, `create_goal` / `get_goal` / `update_goal` (a long brief stays one objective across rounds), `web_search` / `web_fetch`, the three Office tools, and `skill`. It omits schedules, plan mode, `ask_user_question` and `present`: the lead session owns those.
- Mounted tools for the manager preset: the same persistent shell (used to check what a worker changed and to run the check it claims passed), `create_goal` / `get_goal` / `update_goal`, `todo_write`, and `skill`. It mounts no plan mode, `ask_user_question`, `present`, schedules, web tools, image recognition, job controls, or Office tools: it dispatches that work. `send_session_message` comes from the profile's `session-messaging` component; `dispatch_worker` comes from this bundle's `guard.js`, which reuses session-messaging's creation service with the Agent preset fixed to `worker`. The global `create_session_agent` is hidden in the manager scope, so a coordinator cannot start a `personal` or another `manager` session.
- One memory system: the Agent profile's fixed `dsh-auto-memory` component (`memory_*`). None of the presets injects `SOUL.md` / `USER.md` / `MEMORY.md` runtime files; persona comes from `persona.prefix` and the handbook.
- No local `read` / `write` / `edit` / `glob` / `grep` (the shell is the file interface), and no `subagent` / `workflow` (delegation goes through the Agent profile's `session-messaging` component). `working_directory` is supplied by the host for every preset and is not mounted here.

## Choosing a preset

- **Personal Agent**: the session the user talks to. It holds the conversation, the user's preferences, and every outward-facing action.
- **Worker**: a session a lead creates with `create_session_agent` and `agent_preset: worker`, passing a self-contained brief. It does the bounded work, verifies the result, and messages the result back; it does not address the user and does not ask for confirmation.
- **Coordinator**: a session a lead creates with `agent_preset: manager` for one goal that needs several workers or several rounds. It splits the goal, dispatches worker sessions, accepts their evidence, and reports to the lead. One coordinator per goal; it goes no further up, answers to the lead alone, and dispatches one layer down only.

## First run

Start a new session with the **Personal Agent** preset and say hello. If there is no memory of the user yet, the agent offers setup, asks one question at a time, and saves durable answers with `memory_write` into the Agent profile's memory component; it creates no personal files.

## Data and privacy

Memory is managed by the Agent profile's fixed `dsh-auto-memory` component and is not injected into the prompt. Do not put passwords, tokens, API keys, or raw credentials in memory. The persona and handbooks ship with the bundle; they are not user data files.

## Limitations

- Each preset is a single agent, not the multi-agent Router/Worker Super-agent design. Long work goes to a worker session started from the worker preset through the Agent profile's `session-messaging` component.
- In the worker preset, file edits go through the shell, the web uses `web_search` / `web_fetch`, and long shell commands run with `&` and a log file. The persistent shell does not register jobs, so the `job_*` tools currently have no producer. The personal preset mounts none of these; it hands the work to a worker.
- The three Office tools (worker preset) appear only after an Office skill loads; `office_render` also needs an image-capable model route and an attachments service.
- Memory, worker sessions, long-session watching and search come from fixed Agent-profile components: `dsh-auto-memory`, `session-messaging`, and `session-guardian` (including its session-query group). A profile without them exposes no such tools.
- `read_image` (worker preset) needs an image-capable model route and an attachments service.
- The permission mode and sandbox are host/profile settings. None of the presets weakens them.
